# Aliyun Backend Implementation

This document is the minimum production shape for replacing the Supabase
adapter. It deliberately keeps the Flutter-facing contract in
`FOCUS_FLOW_API_CONTRACT.md`; this file describes server ownership, migrations,
and operational boundaries.

## Repository layout

Create a separate `backend/` package at the repository root:

```text
backend/
  package.json
  package-lock.json
  tsconfig.json
  Dockerfile
  .env.example
  src/
    main.ts                 # process startup and graceful shutdown
    app.ts                  # Fastify instance and route registration
    config.ts               # validated environment variables
    db/
      pool.ts
      migrations/
        0001_auth.sql
        0002_core.sql
        0003_courses.sql
        0004_sync.sql
        0005_account.sql
    auth/
      routes.ts
      service.ts
      jwt.ts
      wechat.ts
    sync/routes.ts
    account/routes.ts
    devices/routes.ts
    lib/errors.ts
    lib/validation.ts
  test/
    auth.test.ts
    sync.test.ts
```

Use Fastify, `pg`, `zod`, `jose`, and `argon2`. Keep SQL migrations in source
control and run them from a single release process; the API process must not
silently alter schema on startup.

## Environment

The server environment must provide:

```text
NODE_ENV=production
PORT=8080
DATABASE_URL=postgres://...
JWT_SECRET=<at least 32 random bytes>
JWT_ISSUER=focus-flow
JWT_AUDIENCE=focus-flow-mobile
WECHAT_APP_ID=wx...
WECHAT_APP_SECRET=<server-only secret>
PUBLIC_BASE_URL=https://api.example.com
```

`WECHAT_APP_SECRET`, `DATABASE_URL`, and `JWT_SECRET` must never be placed in
Flutter build arguments, Android resources, Git, or request logs. Production
database access should use TLS and a restricted database role.

## Migration model

All user-owned rows use UUIDs generated by the client or server, a `user_id`
foreign key, `created_at`, `updated_at`, and nullable `deleted_at`. Timestamps
are UTC `timestamptz`; the user's IANA timezone is stored separately.

### `0001_auth.sql`

Create:

- `users(id, email, password_hash, status, created_at, updated_at, deleted_at)`
- `oauth_identities(provider, subject, user_id, profile, created_at, updated_at)`
- `refresh_tokens(id, token_hash, user_id, family_id, expires_at, created_at, revoked_at, replaced_by)`

Unique constraints are `(lower(email))` where an email exists and
`(provider, subject)`. Store only an SHA-256 hash of the opaque refresh token.
Refresh rotation and reuse detection must happen in one database transaction.

### `0002_core.sql`

Port the existing task and note fields from the Supabase migrations, including
`kind`, `location`, `reminder_enabled`, soft deletes, and a monotonic `version`.
Also create `device_tokens` and `user_preferences`. Every query must scope by
the authenticated `user_id`; there is no client-visible service role.

### `0003_courses.sql`

Add the course domain instead of overloading tasks:

- `courses(id, user_id, name, instructor, term, timezone_id, created_at, updated_at, deleted_at, version)`
- `course_lessons(id, course_id, weekday, start_minute, end_minute, room, repeat_rule, created_at, updated_at, deleted_at, version)`
- `course_progress(id, user_id, course_id, lesson_id, progress, completed_at, updated_at, version)`
- `reminders(id, user_id, entity_type, entity_id, remind_at, status, created_at, updated_at)`

Add checks for weekday and minute ranges, and indexes on `(user_id, updated_at)`
and `(user_id, remind_at)` for pending reminders.

### `0004_sync.sql`

Create `sync_cursors(user_id, device_id, cursor, updated_at)` and
`sync_conflicts(id, user_id, entity_type, entity_id, base_version,
local_version, remote_version, local_payload, remote_payload, created_at,
resolved_at)`. Pull responses use a stable `(updated_at, id)` cursor and include
soft-deleted tombstones. Retain tombstones for at least the maximum offline
window (30 days initially); do not purge them while a device cursor can still
reference them.

Push is compare-and-swap: a new row requires `base_version = 0`; an update or
delete requires `base_version = current version` and `version > base_version`.
Return an explicit `conflict` object and never silently overwrite a newer row.

### `0005_account.sql`

Add an append-only `account_events` table for delete/export requests, then make
account deletion idempotent: revoke refresh tokens, invalidate device tokens,
soft-delete or cascade user-owned rows in one transaction, and mark the user
deleted. Export must return tasks, notes, courses, progress, reminders, and
preferences without secrets or token hashes.

## HTTP endpoints

The first deploy should expose only these authenticated, tested routes:

```text
GET  /health
POST /api/auth/email
POST /api/auth/wechat
POST /api/auth/refresh
POST /api/auth/logout
GET  /api/me
POST /api/sync/push
GET  /api/sync/pull
POST /api/devices/token
DELETE /api/devices/token
POST /api/account/delete
POST /api/account/export
```

Access tokens should expire in about 15 minutes. Refresh tokens should be
rotated on every successful refresh and revoked on logout. WeChat login accepts
only the short-lived SDK `code`; the server calls WeChat's code exchange API,
uses `openid` (or `unionid` when available) as the provider subject, and then
returns Focus Flow's own session shape.

## Release gates

Before switching `FOCUS_FLOW_API_URL` on in Flutter:

1. Run migrations against an empty PostgreSQL database and a backup restore.
2. Test email login, WeChat success/cancel/error, refresh rotation, reuse
   detection, logout, and account deletion.
3. Test two devices editing the same task and note, including offline pull,
   tombstone propagation, and explicit conflict responses.
4. Run API tests, Flutter analysis/tests, and Debug plus Release APK/AAB builds.
5. Enable HTTPS, structured request IDs, redacted error logs, database backup,
   and a `/health` check before production DNS is switched.
